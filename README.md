# Мини-система бронирования столиков

Учебный кейс курса «Профессия вайб-кодинг» (модуль PostgreSQL). Бэкенд на
`psycopg2` + графический интерфейс на `tkinter`, три сущности — Гость,
Стол, Бронирование — и надёжная проверка доступности стола.

## Что реализовано

Базовый и средний уровень задания:

- подключение к PostgreSQL через `.env`, автосоздание таблиц `users`,
  `restaurant_tables`, `bookings`;
- полный CRUD для всех трёх сущностей;
- `check_table_availability` — запрет пересекающихся броней одного стола;
- GUI на tkinter с вкладками Гости / Столы / Брони, кнопка «Проверить
  доступность» обязательна и есть.

Плюс доработки сверх задания:

- **Буфер между бронями (15 мин).** Проверка доступности запрещает не только
  точное пересечение интервалов, но и брони впритык — нужен запас времени
  на уборку/пересадку стола. Реальные системы бронирования (OpenTable,
  Resy) как раз страдают от того, что "по времени свободно", а по факту
  стол ещё не готов.
- **Фильтры и поиск** броней по дате, статусу, столу.
- **Полноценный жизненный цикл брони**: `confirmed → cancelled / completed /
  no_show`, с причиной отмены.
- **Понятная сводка после создания брони** — гость, стол, дата, время,
  статус одним окном, чтобы не было ситуации "в приложении подтверждено, а
  на месте — нет".
- **Заметки по гостю** (аллергии, предпочтения, VIP) — поле `notes`.
- **Простая аналитика**: загрузка каждого стола (число активных/завершённых
  броней) и разбивка броней по статусам с процентами.
- **CHECK-ограничения и индекс**: `capacity > 0`, `end_time > start_time`,
  `guests_count > 0`, уникальный `email`/`table_number`, индекс на
  `(table_id, booking_date)`. Проверка "гостей не больше вместимости стола"
  сделана триггером `check_booking_capacity` — PostgreSQL не умеет сверять
  данные из другой таблицы прямо в `CHECK`.

## Структура проекта

```
booking_system/
├── models/
│   ├── user.py           — dataclass User (описывает поля таблицы users)
│   ├── table.py           — dataclass Table
│   └── booking.py         — dataclass Booking
├── postgres_driver.py     — подключение к Postgres, create_tables(), универсальные
│                             обёртки execute_write / execute_returning_id / fetch_all / fetch_one
├── backend.py              — вся бизнес-логика: CRUD, check_table_availability, аналитика
├── seed.py                  — демо-данные: 5 гостей, 5 столов, 6 броней
│                             (с намеренным конфликтом для проверки доступности)
├── app.py                    — GUI на tkinter (точка входа)
├── requirements.txt
├── .env.example
└── README.md
```

## Как запустить

1. Убедиться, что локально запущен PostgreSQL 16 (`brew services start postgresql@16`).
2. Создать роль и базу (один раз):
   ```sql
   CREATE ROLE admin WITH LOGIN PASSWORD 'ваш_пароль';
   CREATE DATABASE booking OWNER admin;
   ```
3. Скопировать `.env.example` в `.env` и вписать реальный пароль.
4. Установить зависимости:
   ```bash
   python3 -m venv venv
   source venv/bin/activate
   pip install -r requirements.txt
   ```
5. Наполнить базу демо-данными (создаст таблицы автоматически):
   ```bash
   python seed.py
   ```
6. Запустить графический интерфейс:
   ```bash
   python app.py
   ```

## Проверка доступности — как продемонстрировать

`seed.py` намеренно бронирует стол №4 на завтра на 19:00–22:00. В GUI на
вкладке «Брони» попробуйте создать бронь на тот же стол и дату на
20:00–21:00 (пересечение) или на 22:05–23:00 (в буфере 15 минут после) —
в обоих случаях кнопка «Проверить доступность» и сама попытка создания
покажут отказ с причиной. Бронь на 22:20 и позже — пройдёт.

## Скриншоты для сдачи

1. Таблицы `users` / `restaurant_tables` / `bookings` в PgAdmin.
2. Список бронирований (вкладка «Брони» в GUI).
3. Проверка доступности с реальным конфликтом (сообщение об отказе).
